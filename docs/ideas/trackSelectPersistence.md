# Track Selection Persistence Design

## Status

The TrackSelect API seam is implemented; the reusable storage, reconciliation, and controller design remains proposed for restoring catalog-track selection across reloads and navigation while retaining the browser session factory pattern.

## Problem

Track Select can initialize catalog-owned tracks from `initialTrackIds`, falling back to `defaultTrackIds`, and report successful submissions through `onCommittedTrackIds`. Browser session factories correctly isolate runtime browser state, but those sessions are intentionally ephemeral: without a host persistence integration, reloading a page or navigating away creates a new session and loses the user's catalog selections.

An earlier implementation associated Track Select state with a session ID. The useful property was not the ID itself; it was that the frontend could choose a stable identity and recover the corresponding selection later.

The new design must preserve that capability without conflating:

- a runtime browser session, which owns stores and must be disposed; and
- a persistence identity, which must survive runtime sessions.

## Goals

- Persist the user's ordered catalog-track selection across reloads and navigation.
- Let the frontend decide whether persistence is per portal, entity, route, cell type, tab, or another product scope.
- Preserve product defaults as the Track Select Reset target.
- Keep fixed non-catalog tracks, such as gene, Manhattan, and LD, outside persisted selection for now.
- Make persistence reusable across applications using `genomebrowser-ui-v2`.
- Keep storage replaceable rather than coupling Track Select directly to `localStorage`.
- Handle stale, malformed, or partially obsolete persisted data safely.
- Integrate persistence cleanup with the browser session lifecycle.

## Non-goals

- Persisting the browser region, highlights, pinned LD state, or fetched data.
- Persisting complete runtime track instances, callbacks, or module objects.
- Moving fixed tracks into Track Select.
- Defining whether every application should persist per entity or per portal.
- Synchronizing selections live between browser tabs or devices.
- Providing server-backed user profiles in the first implementation.

## Core decision

Persistence is a split responsibility:

### The frontend owns policy

The client application chooses:

- the persistence key;
- what product scope that key represents;
- when a key change means the browser session must be replaced;
- which storage adapter to inject.

### `genomebrowser-ui-v2` owns reusable mechanics

The UI library provides:

- separate initial-selection and Reset-default APIs;
- committed-selection notifications;

The proposed reusable persistence layer would also provide:

- persisted payload parsing and version handling;
- catalog-ID reconciliation helpers;
- a storage interface and optional local-storage adapter.

### The browser session owns runtime lifetime

The application browser session composes the injected persistence controller with its track store and disposes any subscriptions when the session ends.

Track Select itself should not choose keys or call `window.localStorage` directly.

## Terminology

### Browser session

An ephemeral object owning one active browser's stores, interactions, subscriptions, and cleanup.

### Persistence key

An opaque, stable string generated by the frontend. It identifies the selection to recover across browser sessions.

### Product defaults

The catalog-qualified IDs that Track Select Reset should restore.

### Initial selection

The catalog-qualified IDs applied once when a new browser session is hydrated. This is the persisted selection when one exists, otherwise the product defaults.

## Why the persistence key must be separate

A generated runtime instance ID cannot restore state after a reload unless the frontend can generate the same ID again. Conversely, a stable route-based key should not imply that the old runtime stores continue to exist.

Examples of valid frontend policies:

```ts
// Shared by every Gene Portal page.
const key = "psychscreen:tracks:v1:gene-portal";

// Separate selection for each gene.
const key = `psychscreen:tracks:v1:gene:${normalizeGene(gene)}`;

// Separate selection for each disease.
const key = `psychscreen:tracks:v1:disease:${encodeURIComponent(disease)}`;

// Shared by browser mode, independent of cell type.
const key = "psychscreen:tracks:v1:single-cell:grn";

// Separate by cell type and mode.
const key = `psychscreen:tracks:v1:single-cell:${normalizeCellType(cellType)}:grn`;
```

The persistence implementation treats these keys as opaque strings.

## Persisted data model

Persist only ordered, catalog-qualified track IDs:

```ts
export type PersistedTrackSelection = {
  schemaVersion: 1;
  trackIds: string[];
  updatedAt?: string;
};
```

Example payload:

```json
{
  "schemaVersion": 1,
  "trackIds": [
    "human-psychscreen::human-psychscreen/epigenetic/adult-bcres",
    "human-psychscreen::human-psychscreen/conservation/240-mammal-phylop-vertical-range"
  ],
  "updatedAt": "2026-07-16T17:00:00.000Z"
}
```

Do not persist complete track instances. Runtime instances may contain module-specific data, callbacks, caches, or implementation details that cannot be safely serialized. Qualified IDs allow current catalogs and registries to reconstruct valid instances.

An empty `trackIds` array is valid and means the user intentionally committed no catalog tracks. It must be distinguishable from a missing or invalid payload.

## Storage abstraction

The reusable package should define a narrow adapter:

```ts
export interface TrackSelectionStorage {
  read(key: string): PersistedTrackSelection | undefined;
  write(key: string, selection: PersistedTrackSelection): void;
  remove(key: string): void;
}
```

The first implementation can be synchronous because browser `localStorage` is synchronous. An async server-backed adapter should be a separate future API rather than making the initial integration ambiguously sync-or-async.

The package may provide:

```ts
export function createLocalStorageTrackSelectionStorage(options?: {
  namespace?: string;
}): TrackSelectionStorage;
```

The adapter should:

- tolerate unavailable browser storage;
- catch malformed JSON and storage exceptions;
- avoid throwing during server rendering;
- return `undefined` for missing or invalid payloads;
- leave key generation to the application.

Applications may inject another implementation for tests, memory-only behavior, or future user-profile storage.

## Track Select API

TrackSelect separates two responsibilities that were previously both served by `defaultTrackIds`:

1. initializing a new store; and
2. defining Reset behavior.

Passing persisted IDs as `defaultTrackIds` would incorrectly make Reset restore the previous user selection instead of product defaults.

Implemented API:

```ts
export type TrackSelectProps = {
  // Existing product baseline and Reset target.
  defaultTrackIds?: readonly string[];

  // Applied once for a newly owned Track Select/browser session.
  // When omitted, defaultTrackIds remains the initialization fallback.
  initialTrackIds?: readonly string[];

  // Called only after catalog changes are successfully committed to the store.
  onCommittedTrackIds?: (trackIds: readonly string[]) => void;
};
```

Usage:

```tsx
<TrackSelect
  trackCatalogs={trackCatalogs}
  useTrackStore={trackStore}
  initialTrackIds={persistedTrackIds ?? defaultTrackIds}
  defaultTrackIds={defaultTrackIds}
  onCommittedTrackIds={persistence.commit}
/>
```

## Track Select semantics

### Initialization

- `initialTrackIds` is applied once to a new Track Select/browser-session owner.
- If `initialTrackIds` is `undefined`, initialization falls back to `defaultTrackIds`.
- `initialTrackIds={[]}` intentionally initializes with no catalog tracks.
- Non-catalog tracks remain preserved in their existing order.
- Catalog tracks follow the supplied initial order.
- Initial hydration should not trigger a persistence write.

Changing persistence identity should replace the owning session/component. Dynamically changing `initialTrackIds` on an existing session is not the normal rehydration mechanism.

### Submit

- Track Select applies the draft atomically as it does today.
- Only after a successful store update does it call `onCommittedTrackIds`.
- The callback receives all committed catalog-owned IDs in browser order.
- A failed submission does not write persistence.

### Clear

- Clear continues to edit only the draft.
- Clear followed by Cancel does not persist.
- Clear followed by successful Submit calls the callback with `[]`.

### Reset

- Reset restores `defaultTrackIds` in the draft, not `initialTrackIds`.
- Reset does not persist until the user successfully submits the draft.
- Successful submission after Reset persists the product-default IDs.

### Cancel and dismissal

- Cancel, close, and ordinary dismissal discard the draft.
- They do not call the committed-selection callback.

## Reconciliation and validation

Product defaults are authored configuration and should continue to validate strictly. Invalid default IDs should surface as application errors.

Persisted IDs are user data that may outlive catalog changes. Reconciliation should be tolerant:

1. Parse and validate the payload shape and schema version.
2. Preserve the supplied order.
3. Remove duplicate IDs after their first occurrence.
4. Remove IDs not present in the supplied catalogs.
5. Confirm remaining track types are supported by the session registry.
6. Enforce the configured maximum track count.

Recommended fallback behavior:

- Missing, malformed, or version-incompatible payload: use product defaults.
- Explicit persisted `[]`: preserve the empty selection.
- Some IDs remain after reconciliation: use the valid subset.
- A non-empty payload becomes entirely empty because every ID is obsolete: treat it as stale and use product defaults.

Applications can force a new baseline by changing the persistence key version, for example from `v1` to `v2`.

## Reusable persistence controller

The UI package should provide mechanics that clients do not need to rewrite:

```ts
type CreateTrackSelectionPersistenceOptions = {
  key: string;
  storage: TrackSelectionStorage;
  trackCatalogs: readonly unknown[];
  registry: ModuleRegistry;
  defaultTrackIds: readonly string[];
  maxTracks?: number;
};

type TrackSelectionPersistence = {
  initialTrackIds: readonly string[];
  defaultTrackIds: readonly string[];
  commit(trackIds: readonly string[]): void;
  clear(): void;
  dispose(): void;
};
```

Conceptual construction:

```ts
const persistence = createTrackSelectionPersistence({
  key: persistenceKey,
  storage,
  trackCatalogs,
  registry: trackStore.getState().registry,
  defaultTrackIds,
});
```

The controller reads and reconciles persisted IDs during construction. `commit` writes a versioned payload. `dispose` exists so future adapters can add subscriptions without changing the browser-session contract.

The initial implementation should persist successful Track Select commits rather than subscribe to every track-store mutation. Track stores also change for hover interactions, configuration updates, and fixed tracks; watching every mutation would require extra filtering and could cause unnecessary writes.

If applications later need programmatic catalog-track mutations to persist, the controller can subscribe to the track store and compare a derived qualified-ID signature. That should be an explicit extension, not accidental behavior.

## Browser session integration

The runtime browser session is the correct composition and cleanup boundary, but storage remains injected:

```ts
type TrackSelectionSessionConfig = {
  key: string;
  storage: TrackSelectionStorage;
  trackCatalogs: readonly unknown[];
  defaultTrackIds: readonly string[];
};

type GenomeBrowserSession = {
  browserStore: BrowserStoreInstance;
  trackStore: TrackStoreInstance;
  trackSelection?: TrackSelectionPersistence;
  setRegion(region: BrowserRegion): void;
  dispose(): void;
};
```

A portal factory may accept the selection configuration:

```ts
const session = createGenePortalBrowserSession(region, {
  trackSelection: {
    key: persistenceKey,
    storage,
    trackCatalogs: MAIN_TRACK_CATALOGS,
    defaultTrackIds: GENE_PORTAL_DEFAULT_TRACK_IDS,
  },
});
```

Session creation order:

1. Create the browser and track stores.
2. Register the modules required by the supplied catalogs.
3. Create fixed non-catalog tracks.
4. Create the persistence controller using the store registry.
5. Expose the controller's initial/default IDs and commit callback to the view.
6. Dispose the controller with the session.

The view remains presentation-oriented:

```tsx
<GenomeBrowserView
  browserStore={session.browserStore}
  trackStore={session.trackStore}
  trackCatalogs={catalogs}
  initialTrackIds={session.trackSelection?.initialTrackIds}
  defaultTrackIds={session.trackSelection?.defaultTrackIds}
  onCommittedTrackIds={session.trackSelection?.commit}
/>
```

An application may instead compose the controller in a React hook if its architecture prefers that. The required boundary is the same: the app chooses policy, the reusable package handles mechanics, and the controller lifetime matches the browser session.

## Route and identity lifecycle

Frontend routers may reuse a component while changing route parameters. A persistence-key change must be treated as a browser-session identity change.

Otherwise, a session created for `APOE` could remain alive after navigation to `MAPT` and save its old selection under the new key.

Recommended owner:

```tsx
function GenePage({ gene }: { gene: string }) {
  const persistenceKey = useMemo(() => `psychscreen:tracks:v1:gene:${normalizeGene(gene)}`, [gene]);

  return <GeneBrowserPanel key={persistenceKey} persistenceKey={persistenceKey} gene={gene} />;
}
```

The key causes React to unmount the old owner, dispose its runtime session, and create a session hydrated from the new persistence identity.

Use this only for construction-time identity changes. Ordinary region updates within the same browser identity should continue through `session.setRegion`.

## Example client policies

### Per-gene selection

```ts
const persistenceKey = `psychscreen:tracks:v1:gene:${normalizeGene(geneFromRoute)}`;
```

Reloading or returning to the same gene restores that gene's selection. Different genes can diverge.

### Portal-wide Gene selection

```ts
const persistenceKey = "psychscreen:tracks:v1:gene-portal";
```

Every gene shares one viewing preference. The route changes the region and fixed data but not catalog selection.

### Single Cell tab selection

```ts
const atacKey = "psychscreen:tracks:v1:single-cell:atac";
const grnKey = "psychscreen:tracks:v1:single-cell:grn";
const qtlKey = "psychscreen:tracks:v1:single-cell:qtl";
```

Each mode persists independently. Separate browser sessions already provide the matching runtime isolation.

### Per-cell-type GRN selection

```ts
const persistenceKey = `psychscreen:tracks:v1:single-cell:${normalizeCellType(cellType)}:grn`;
```

Use this only if product behavior truly expects each cell type to maintain a distinct selection. It creates more stored entries and may be harder for users to reason about.

## Failure behavior

Persistence should never prevent the browser from loading.

- Storage unavailable: initialize with product defaults.
- Read throws: initialize with product defaults.
- Payload malformed: ignore it and use defaults.
- Catalog entry removed: retain valid remaining IDs.
- Module unavailable for a stored ID: remove that ID.
- Write fails: keep the successful in-memory selection and optionally report a non-blocking error.
- Storage quota exceeded: keep the in-memory selection.

The application may log or surface storage failures, but Track Select submission should not be rolled back after the track store was already updated successfully.

## SSR and hydration

The local-storage adapter must not access `window` during server rendering. For SSR applications, persistence hydration should occur on the client before Track Select initializes catalog tracks.

Possible integration strategies:

- create the browser session only in a client-owned component;
- expose a `ready` state and delay Track Select mounting until storage has been read; or
- use a synchronous client-only adapter in applications where the browser itself is client-only.

The implementation should avoid first applying defaults and then replacing them with persisted IDs visibly after paint.

## Security and privacy

Persisted values are catalog identifiers, not arbitrary executable configuration. Even so:

- validate every stored ID against current catalogs;
- never instantiate a track directly from untrusted serialized config;
- do not include route entities or user identifiers in keys without considering local privacy requirements;
- treat local storage as readable and mutable by the browser user.

## Pros

- The frontend retains complete control over persistence scope.
- Track Select remains reusable and storage-agnostic.
- Product defaults retain correct Reset semantics.
- Runtime browser sessions remain disposable and isolated.
- Persisted data is small, versionable, and resilient to implementation changes.
- Other projects can reuse validation and storage mechanics without copying application code.
- Future storage adapters can be introduced without changing catalog or session concepts.

## Cons and tradeoffs

- Track Select needs a new API separating initial IDs from defaults.
- Route identity changes require deliberate session replacement.
- Catalog evolution requires reconciliation and version policy.
- Local storage is device/browser-specific and does not follow authenticated users.
- Session construction gains another optional integration concern.
- A future async/server adapter will require a separate hydration lifecycle.

## Alternatives considered

### Put `localStorage` directly in Track Select

Rejected because it couples a reusable UI component to one environment and gives it no principled way to choose route/product keys.

### Let every client implement persistence independently

Rejected because clients would duplicate payload validation, stale-ID reconciliation, Reset semantics, and error handling.

### Persist the complete track store

Rejected because runtime track instances contain module-owned and potentially non-serializable state. Catalog-qualified IDs are the stable reconstruction boundary.

### Use persisted IDs as `defaultTrackIds`

Rejected because Reset would restore the user's prior selection instead of product defaults.

### Make persistence key equal runtime session ID

Rejected unless the frontend deliberately supplies a stable value. Random runtime IDs cannot recover state after reloads.

## Suggested implementation sequence

1. [x] Add `initialTrackIds` and `onCommittedTrackIds` to Track Select, with omitted initial IDs falling back to defaults and Reset without defaults clearing the catalog draft.
2. Add payload parsing, reconciliation, and a `TrackSelectionStorage` interface to `genomebrowser-ui-v2`.
3. Add a safe local-storage adapter.
4. Add the headless persistence controller.
5. Extend the application browser-session composition to accept an optional persistence configuration.
6. Let each portal generate its desired stable key.
7. Verify initialization, Submit, Clear, Reset, Cancel, malformed storage, stale IDs, and route identity changes.

## Acceptance criteria

- Reloading a browser restores the committed ordered catalog selection for its frontend-generated key.
- Navigating away and returning restores the same selection.
- Different keys remain isolated.
- A committed empty selection restores as empty.
- Reset restores product defaults, not the persisted initial selection.
- Cancel and dismissed drafts do not modify persistence.
- Unknown persisted IDs do not break Track Select or the browser.
- Fixed non-catalog tracks remain present and are not serialized.
- Changing the persistence key replaces and disposes the previous runtime session.
- Storage failures do not prevent normal in-memory browser use.
- Applications can replace local storage without changing Track Select behavior.
