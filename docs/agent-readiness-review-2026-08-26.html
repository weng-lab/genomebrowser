This repo catches domain logic regressions. It does not reliably catch broken product behavior.

A capable agent can make a plausible app or UI change, run the required command, and get a clean result. Tests are strongest where the right answer is mechanical. They are weakest where an agent must judge whether the product still works.

The original evidence came from five independent read-only reviews, direct source inspection, pnpm verify, a full React Doctor scan, and repository test counts. The 31 August update rechecked every finding against the current repository and removed resolved items.

The repo explains intent and tests domain mechanics well. Feedback stops before the final product. The deployed standalone app, browser behavior, accessibility, responsive layout, and complete package integration remain largely unchecked.

What works well

Ownership has one named source

AGENTS.md and DESIGN.md assign runtime, first-party tracks, collection UI, and product composition to named packages. An agent has a concrete reason not to put behavior in whichever package happens to be nearby.

AGENTS.md:5-17 · DESIGN.md:14-20

Core hides real complexity

defineTrackModule turns one definition into validation, defaults, schemas, creation, rendering, fetching, settings, and tooltips. The track store and data coordination modules also keep high-risk rules in one place.

packages/core/src/modules/defineTrackModule.ts:108-194 · docs/core/adr/0006-browser-features-are-deep-modules-with-narrow-apis.md

Reader fixtures can be checked independently

Committed binaries include generation commands, tool versions, hashes, UCSC output, compression variants, edge intervals, and a separate inspector. An agent can compare exact results without calling a live server or trusting the code under test.

packages/reader/test/fixtures/bigwig/README.md:1-189

Tests cover failures that types cannot catch

The suite checks stale async completion, rejected updates without partial state, cancellation, malformed ranges, renderer isolation, data privacy, cache lifetime, and fetch invalidation. These tests catch bugs that a valid type signature would miss.

packages/core/test/data/useTrackData.test.tsx · packages/reader/test/httpRange.test.ts · packages/core/test/browser/trackRenderErrorIsolation.test.tsx

Reader and tracks test the built packages

After Vite builds, reader checks its root export and declaration boundaries, while tracks checks its public subpaths and isolated implementation graphs. Both also check ESM output and source maps. Source tests alone would not catch these packaging failures.

packages/reader/scripts/verify-package.mjs · packages/tracks/scripts/verify-package.mjs

ADRs explain the constraints

The core ADRs explain state validation, panning settlement, deep browser modules, configuration ownership, and authenticated transport. An agent can reject a locally convenient change because the repo records why the constraint exists.

docs/core/adr/0001-0010 · docs/ui/adr/0001

Where agents get false confidence

Critical

The deployed app has no tests

apps/standalone owns the deployed product, but its package defines no test script and contains zero test files. Turbo treats the missing task as acceptable. Broken toolbar wiring, TrackSelect opening, clipboard behavior, or GraphQL proxy semantics can pass pnpm verify. The experimental playground has no tests either.

apps/standalone/package.json:5-14 · apps/standalone/components/Browser.tsx · apps/standalone/app/api/screen-graphql/route.ts

Critical

The TrackSelect workflow test does not render its visible content

trackSelectWorkflow.test.tsx sometimes renders the TrackSelect wrapper, but replaces TrackSelectContent with a hook probe that returns null. Its 28 tests check state semantics. They cannot show that Submit calls the action, failures appear on screen, the dialog stays open, or controls have accessible names.

packages/ui/test/trackSelectWorkflow.test.tsx:26-39,217-869 · docs/ui/testing.md:43-54

Critical

Agents cannot run the documented UI checks

DESIGN.md requires checks at narrow widths, keyboard operation, accessible inputs, disabled and error states, and long content. The repo assigns those checks to an intentionally unrouted playground example, while agents may not start the development server. It also does not require agents to report those checks as unverified.

DESIGN.md:39-64 · docs/ui/testing.md:25-33 · apps/playground/examples/ui/App.tsx · apps/playground/README.md:9-15

High

No test covers reader → track → browser

Reader tests use real files. Track tests mock the reader. Cross-package fetch tests mock each fetcher. No test mounts a first-party track, reads a committed binary fixture, and renders it through GenomeBrowser.

packages/tracks/test/core/bigwig.test.ts:4-13 · packages/tracks/test/core/fetchOnChange.integration.test.tsx:31-41

High

pnpm verify skips named checks

pnpm verify does not explicitly run the root typecheck task, React Doctor, browser tests, coverage, Rust checks, or release validation. Library builds depend on typecheck, and both Next builds currently run TypeScript, but each app overrides the root build dependency and does not require its separate typecheck command. CI now runs Rust tests separately. React Doctor remains non-blocking.

package.json:12-23 · turbo.json:9-29 · apps/standalone/turbo.json:1-8 · .github/workflows/ci.yml:30-34 · .github/workflows/react-doctor.yml:33-38

High

test.md is stale but looks authoritative

packages/reader/test.md tells an agent to design an interface from a missing spec and an external checkout. Its claims about uncached reads and sorting conflict with current docs. A search-driven agent has no clear reason to ignore it.

packages/reader/test.md:1-32 · packages/reader/README.md:135-143

Problem. Two deep public modules repeat the same validation, range, cache, cancellation, R-tree, and block-loading implementation.

Solution. Keep both public interfaces, but put their common query lifecycle behind one internal interface with format-specific adapters.

  • locality: one abort policy
  • leverage: two formats
  • tests hit public interfaces

Documentation and skill friction

Targeted commands conflict

Root guidance requires Turbo filters. Package testing docs and the first-party track skill use direct pnpm --filter commands.

docs/turborepo.md:29-39 · docs/core/testing.md:3-13 · docs/ui/testing.md:3-12

One track list is stale

The root README and package docs now include Gene, but the core-facing track inventory still omits it.

docs/core/tracks/README.md:7-13 · packages/tracks/src/lib.ts:10-19

The index.ts rule needs an exception

docs/conventions.md bans every index.ts, while track authoring requires public subpath entry files with that name.

docs/conventions.md:13-17 · docs/core/tracks/sourceLayout.md:3-9

Idea docs do not share a status convention

Some idea docs identify themselves as proposals. Others describe behavior that does not exist without saying whether the text is current, planned, or abandoned.

docs/ideas/browserSessions.md · docs/ideas/trackPrimitives.md:1-5

Recommended order

  1. 1. Test the deployed app. Add an apps/standalone test task with smoke tests for shell composition, toolbar actions, TrackSelect opening, and the GraphQL route.
  2. 2. Test one complete visible TrackSelect failure path. Keep the strong state tests, but render the real content and assert an actionable error, open dialog, and unchanged store.
  3. 3. Add one vertical integration test. Use a committed reader fixture through a first-party track and GenomeBrowser. This is more valuable than broad coverage targets.
  4. 4. Make verify say exactly what it checks. Include app typecheck directly, decide which browser and React Doctor checks should block changes, and fail when a package lacks a required task.
  5. 5. Remove misleading authority. Delete or relocate packages/reader/test.md, reconcile targeted-command guidance, and correct the remaining stale track inventory.
  6. 6. Deepen the two strongest architecture candidates. Concentrate the BBI query lifecycle and generic signal behavior after the verification gaps are closed.

Top recommendation

Close the app and rendered-workflow verification gap first.

Domain code already has strong deterministic feedback. App tests and one real visible workflow would prevent more wrong-but-plausible changes than another set of isolated unit tests.
