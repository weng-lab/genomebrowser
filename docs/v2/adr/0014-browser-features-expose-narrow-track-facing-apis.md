# Browser features expose narrow track-facing APIs

Browser-backed capabilities are owned by the browser feature that implements them, and that feature may expose a small, explicit track-facing API when track modules need to participate. For example, tooltip behavior belongs to the browser tooltip feature, which can expose `useTooltip`; track-height behavior belongs to the browser track-height feature, which can expose `useAutoTrackHeight`; tracks should import these focused feature entry points rather than a generic runtime context, while continuing to avoid browser orchestration internals such as `GenomeBrowser`, browser stores, viewport implementation, and feature-private files.

This treats browser features as deep modules: each feature hides its providers, stores, DOM/SVG coordination, and browser integration behind a narrow API that both the browser and track modules can use. The module system remains responsible for defining what track modules are, while browser features own the browser-backed capabilities they provide; this keeps seams few, specific, and tight without forcing all track-facing browser behavior through `src/modules/runtime` or another middleman.
